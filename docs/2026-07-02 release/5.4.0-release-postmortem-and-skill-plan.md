# Ghostex 5.4.0 Release Postmortem And Fresh Skill Plan

Date: 2026-07-02

## Why The Release Took So Long

The release was slow because it was not just one clean `release:local` run. It included release-bound code churn, stale required Linux remote packages, toolchain recovery, Apple notarization, large GitHub/Homebrew network transfers, Android packaging, and final live validation.

The main time costs were:

- Release-bound source kept changing before the release could freeze.
  - After the 5.4.0 changelog/docs commit, new GPUI named workspace group files appeared.
  - After the first push, more GPUI runtime and sidebar CSS edits appeared.
  - After the second push, another GPUI runtime rendering edit appeared.
  - Because the release rule is "commit and push all latest release-bound code, do not stash," each batch had to be inspected, typechecked, split into commits, pushed, and rechecked.
  - This was correct, but it turned the release into a moving-target release.

- `bun run test` is currently a bad release gate.
  - It ran for about 5 minutes and then failed.
  - It discovered bundled `code-server`, built app copies, and generated output instead of only repo-owned tests.
  - It reported thousands of failed discovered files plus stale source-contract test failures.
  - Useful signal came from `bun run typecheck`, targeted Cargo checks, Android readiness checks, and the release script validators, not from the current root test command.

- Remote Linux gxserver packages were stale and mandatory.
  - The release script requires `build/remote-gxserver-linux/{x64,arm64}/package` to match the exact source revision being released.
  - Existing packages were built from `e9b1788...`, while 5.4.0 released `e00f7ee...`.
  - The documented `bun run gxserver:remote-linux` refused on macOS without `--allow-cross`.
  - The cross build then hit several local toolchain issues:
    - missing `x86_64-linux-gnu-gcc`,
    - Zig 0.16 rejecting Rust-style `--target=x86_64-unknown-linux-gnu`,
    - macOS `ar` producing an unusable Linux SQLite static archive,
    - zmx/Ghostty requiring Zig 0.15.2 while zehn requires Zig 0.16.0.
  - Once the right wrapper/env setup was found, the package builds themselves were fast. The time was lost rediscovering the exact cross-build recipe.

- Apple notarization alone took 16 minutes 35 seconds.
  - This is mostly external Apple processing time.
  - The DMG was accepted, stapled, and validated, but that wait is not avoidable from the agent side.

- The macOS DMG is large.
  - The published DMG was 827,750,415 bytes.
  - GitHub upload took several minutes.
  - Live GitHub download validation took several minutes.
  - Homebrew `brew fetch` downloaded the same large DMG again.
  - These checks are valuable, but they are network-bound and expensive.

- Android release was not the main bottleneck.
  - CLI tests passed in about 9 seconds.
  - Gradle release build/checks finished in about 41 seconds.
  - APK upload added some network time.
  - Connected-device E2E and first-run UI smoke were skipped because the release used the local path without a connected device.

- Homebrew added extra network and tap update time.
  - The cask commit/push was quick.
  - `brew update --force` updated multiple taps.
  - `brew fetch --force --cask --arch=arm` downloaded the large DMG again.

## Exact Remote Linux Cross-Build Recipe Used

This should become a checked-in script instead of being rediscovered during release.

```sh
mkdir -p /tmp/ghostex-linux-cross-cc

cat > /tmp/ghostex-linux-cross-cc/x86_64-linux-gnu-cc <<'EOF'
#!/bin/sh
args=()
for arg in "$@"; do
  case "$arg" in
    --target=x86_64-unknown-linux-gnu|-target|x86_64-unknown-linux-gnu) ;;
    *) args+=("$arg") ;;
  esac
done
exec zig cc -target x86_64-linux-gnu "${args[@]}"
EOF

cat > /tmp/ghostex-linux-cross-cc/aarch64-linux-gnu-cc <<'EOF'
#!/bin/sh
args=()
for arg in "$@"; do
  case "$arg" in
    --target=aarch64-unknown-linux-gnu|-target|aarch64-unknown-linux-gnu) ;;
    *) args+=("$arg") ;;
  esac
done
exec zig cc -target aarch64-linux-gnu "${args[@]}"
EOF

cat > /tmp/ghostex-linux-cross-cc/zig-ar <<'EOF'
#!/bin/sh
exec zig ar "$@"
EOF

chmod +x /tmp/ghostex-linux-cross-cc/x86_64-linux-gnu-cc \
  /tmp/ghostex-linux-cross-cc/aarch64-linux-gnu-cc \
  /tmp/ghostex-linux-cross-cc/zig-ar
```

Build x64:

```sh
env \
  CC_x86_64_unknown_linux_gnu=/tmp/ghostex-linux-cross-cc/x86_64-linux-gnu-cc \
  AR_x86_64_unknown_linux_gnu=/tmp/ghostex-linux-cross-cc/zig-ar \
  CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_LINKER=/tmp/ghostex-linux-cross-cc/x86_64-linux-gnu-cc \
  ZMX_ZIG=/Users/madda/.local/share/mise/installs/zig/0.15.2/bin/zig \
  TUI_ZIG=/Users/madda/.local/share/mise/installs/zig/0.15.2/bin/zig \
  ZEHN_ZIG=/opt/homebrew/bin/zig \
  node gxserver-rs/package-remote-linux.mjs --arch x64 --allow-cross
```

Build arm64:

```sh
env \
  CC_aarch64_unknown_linux_gnu=/tmp/ghostex-linux-cross-cc/aarch64-linux-gnu-cc \
  AR_aarch64_unknown_linux_gnu=/tmp/ghostex-linux-cross-cc/zig-ar \
  CARGO_TARGET_AARCH64_UNKNOWN_LINUX_GNU_LINKER=/tmp/ghostex-linux-cross-cc/aarch64-linux-gnu-cc \
  ZMX_ZIG=/Users/madda/.local/share/mise/installs/zig/0.15.2/bin/zig \
  TUI_ZIG=/Users/madda/.local/share/mise/installs/zig/0.15.2/bin/zig \
  ZEHN_ZIG=/opt/homebrew/bin/zig \
  node gxserver-rs/package-remote-linux.mjs --arch arm64 --allow-cross
```

Verify:

```sh
HEAD="$(git rev-parse HEAD)"
for arch in x64 arm64; do
  jq . "build/remote-gxserver-linux/$arch/package/build-identity.json"
  test "$(jq -r .sourceRevision "build/remote-gxserver-linux/$arch/package/build-identity.json")" = "$HEAD"
  test "$(jq -r .sourceDirty "build/remote-gxserver-linux/$arch/package/build-identity.json")" = "false"
done
```

## What To Fix Before The Next Release

These are the changes that would make the next release much faster:

- Add a real release freeze step.
  - After source commits are pushed, run a stability check that waits for the worktree to stay clean for a short window.
  - If source files change after push, loop back to inspect/commit/push before any package build starts.
  - This avoids discovering late source edits after expensive release work has begun.

- Replace `bun run test` as the release gate.
  - Either fix Vitest excludes so it does not discover `code-server`, built app bundles, `build/`, `native/macos/ghostexHost/Web/`, or `gpui/build/`, or create a dedicated `bun run test:release`.
  - The release gate should run focused repo-owned checks only.
  - Keep root `bun run test` out of the release skill until it is trustworthy.

- Script the remote Linux package cross-build.
  - Add `scripts/build-remote-gxserver-linux-release.sh`.
  - It should create the temporary Zig CC/AR wrappers, resolve Zig 0.15.2 for zmx/TUI and Zig 0.16.0 for zehn, build both arches, and validate build identity.
  - The skill should call that script, not hand-type env vars.

- Prefer CI-produced Linux remote packages.
  - Best version: CI builds x64 and arm64 remote packages on Ubuntu for every pushed main commit and uploads them as artifacts keyed by source revision.
  - Local release then downloads artifacts for the current commit.
  - This removes the most fragile local toolchain work from release day.

- Reduce duplicate large DMG downloads.
  - Keep one live published-asset verification, but avoid downloading the same 828 MB DMG multiple times when GitHub digest and Homebrew fetch already prove the same URL/SHA.
  - If Homebrew fetch is mandatory, reuse its cached artifact path for final checksum where possible.

- Split release automation into explicit phases.
  - `preflight`: clean/synced/tag absent/changelog valid/secrets/subrepos.
  - `prepare-remote-linux`: build or fetch current Linux packages.
  - `publish-macos`: run macOS build/sign/notary/appcast/GitHub DMG.
  - `publish-android`: build/upload Android APK.
  - `publish-homebrew`: update/fetch cask.
  - `verify-live`: independent checks.
  - Each phase should be resumable and should print a timing summary.

- Add duration logging to `scripts/release-ghostex.mjs`.
  - The script should print elapsed time per phase at the end.
  - That would make future bottlenecks obvious without reconstructing them from terminal output.

## Fresh Skill Implementation Plan

Create a new skill named `ghostex-release-operator`.

The current `ghostex-release-flow` skill has too much historical detail inline. The fresh skill should be shorter and stricter: a small `SKILL.md` that always calls deterministic scripts and reads focused references only when needed.

Proposed folder:

```text

├── SKILL.md
├── agents/

└── references/
    ├── standard-release.md
    ├── remote-linux-packages.md
```

Proposed repo scripts the skill should rely on:

## Expected Time After These Fixes

Best realistic target:

- Source freeze and commits: 5-10 minutes if no late edits appear.
- Remote Linux packages: 1-3 minutes locally once scripted, or near-zero if downloaded from CI.
- macOS build/sign/package: 5-8 minutes when cached.
- Apple notarization: 10-20 minutes, external.
- GitHub/Sparkle/Homebrew/Android publication: 10-15 minutes, mostly network.
- Final verification: 3-5 minutes.

So a clean release can probably drop from about an hour to 30-40 minutes. It cannot reliably be 5-10 minutes while Apple notarization, 828 MB DMG upload/download, Android, and Homebrew fetch remain in scope.

The biggest controllable wins are:

1. stop root `bun run test` from wasting time,
2. script or CI-build remote Linux packages,
3. freeze the worktree before release starts,
4. reduce duplicate live DMG downloads,
5. add phase timing so slow steps are obvious immediately.
